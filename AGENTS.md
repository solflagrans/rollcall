# Rollcall: руководство для разработки

## Назначение документа

Этот файл содержит устойчивые инженерные, продуктовые и визуальные правила Rollcall. Перед изменениями изучи существующую реализацию затрагиваемого модуля и следуй уже принятому паттерну.
Не создавай параллельную архитектуру для похожего сценария и не переделывай завершённые области без прямой необходимости.

`README.md` предназначен для пользовательского описания продукта. Не переноси туда внутренние схемы таблиц, списки маршрутов, устройство репозиториев, подробные команды проверок или правила работы агента.

## Принципы работы

- Сначала найди владельца поведения через `rg`: маршрут, компонент, схему, сервис, репозиторий и таблицу. Меняй источник истины, а не маскируй проблему на уровне страницы.
- Сохраняй модульный монолит и текущие границы `src/features/*`.
- Придерживайся KISS и DRY: выноси общее только при реальном повторении или наличии устойчивого предметного понятия. Не создавай абстракции «на будущее» без ближайшего потребителя.
- Следуй SOLID прагматично: предметные правила принадлежат сервисам и чистым функциям, доступ к данным скрыт за портами репозитория, UI не должен знать детали Drizzle.
- Не смешивай попутный рефакторинг с продуктовой задачей. Сохраняй не относящиеся к запросу изменения и не удаляй существующий код только потому, что он кажется избыточным.
- Пользовательские строки, варианты enum и их представление централизуй в словарях `presentation`, если они используются более чем в одном месте или зависят от предметного типа.
- Не раскрывай секреты и содержимое `.env.local` в логах, ответах, тестовых данных или клиентском bundle.

## Архитектура

Основной поток зависимости:

```text
app route / component
        ↓
Server Action или route-context
        ↓
application service
        ↓
repository port
        ↓
Drizzle repository + PostgreSQL
```

### App Router

- Страницы и layout по умолчанию оставляй Server Components.
- Клиентскую границу вводи на минимальном интерактивном поддереве: формы, Dialog, меню, локальное
  состояние и браузерные API.
- Страницы отвечают за получение route-context, канонизацию URL и композицию представления. Не
  помещай в них бизнес-правила и сложные запросы.
- Динамические параметры Next.js обрабатывай как `Promise`, согласно локальной документации этой
  версии Next.js.
- Некорректные ссылки обрабатывай через существующие route-context helpers: сначала проверяется группа, затем вложенная сущность. Для отсутствующей группы переходи к созданию группы, для отсутствующей вложенной сущности — в группу, сохраняя понятное уведомление.

### Feature-модули

Используй существующую структуру, когда слою есть реальная работа:

```text
src/features/<feature>/
├── components/       # feature UI
├── domain/           # модели и чистые предметные функции
├── presentation/     # словари, подписи, view-model и форматирование
├── server/           # service, repository port, Drizzle adapter, route-context
├── actions.ts        # тонкие Server Actions
└── schemas.ts        # Zod-схемы и нормализация входа
```

- Server Action валидирует границу, вызывает операцию, преобразует ожидаемую ошибку в
  пользовательский результат и выполняет только необходимую навигацию/инвалидацию.
- Сервис содержит инварианты и оркестрацию. Он не зависит от React, Next.js или конкретного
  Drizzle-клиента.
- Репозиторий выражает нужды сервиса, а не копирует API ORM.
- Чистую сортировку, вычисляемые состояния и массовые преобразования держи в `domain` и покрывай быстрыми unit-тестами.
- Общие технические helpers размещай в `src/lib` только если они не принадлежат одному feature.

### База данных и миграции

- PostgreSQL и Drizzle — постоянный источник данных. Сервер не создаёт и не восстанавливает схему автоматически при запуске.
- Любое изменение схемы оформляй новой Drizzle-миграцией. Не исправляй уже применённую миграцию задним числом.
- Базовые инварианты дублируй ограничениями базы, когда это надёжно выражается: внешние ключи, уникальность, check constraints и индексы.
- Проверки, зависящие от нескольких агрегатов или пользовательского сценария, оставляй в сервисе.
- Физическое удаление исторически значимых сущностей должно быть `RESTRICT` или предварительно проверяться на зависимости. Деактивация и архивирование не равны удалению.
- UUID остаётся внутренним ключом. Во внешних URL используй короткий уникальный `publicId` и перенаправляй старый/неканонический адрес на канонический.
- Для связанных записей используй атомарную операцию. Учитывай, что Neon HTTP driver не поддерживает обычный `db.transaction`; применяй поддерживаемый атомарный batch-паттерн проекта.

## Продуктовые инварианты

### Группа и учебные периоды

- Тип периодов — обязательное свойство группы: `semester`, `trimester`, `quarter` или `year`.
- Конкретные названия и действия зависят от типа: «Семестры», «Новая четверть», «Новый учебный год» и т. п. Используй единый словарь period copy.
- Название периода вычисляется как `{номер} {тип}`. Название, календарный статус и выбранность в базе не хранятся.
- Одинаковые номера периодов допустимы. Пересечение дат периодов одной группы запрещено.
- Нарушение хронологии номеров — мягкое компактное предупреждение, а не блокировка сохранения.
- Статус периода вычисляется по date-only датам в часовом поясе пользователя.
- Последний открытый период не запоминается. Период по умолчанию выбирается детерминированно: текущий, затем ближайший предстоящий, затем последний завершённый.
- Если в периоде есть занятия, его новые границы не могут исключить самое раннее или самое позднее занятие. Показывай конкретную конфликтующую дату.

### Состав группы

- `GroupMember` принадлежит непосредственно группе и не зависит от учебных периодов.
- Имя и фамилия обязательны и хранятся раздельно. Email необязателен, нормализуется и уникален
  среди непустых email одной группы.
- Роли: `headman`, `deputy`, `student`. Староста единственный, всегда активен и не получает обычные действия изменения, деактивации и удаления.
- Пока старосты нет, показывай onboarding «Добавить старосту». После этого обычная форма позволяет выбрать только студента или заместителя.
- Деактивация сохраняет предметную сущность и переносит участника в неактивный состав. Возврат активирует ту же запись. Удаление предназначено только для ошибочно созданной записи и блокируется связанными данными.
- Базовая сортировка — фамилия по возрастанию. Не группируй состав по ролям.

### Дисциплины

- Дисциплина принадлежит группе. Учебные периоды подключают дисциплины общего пула через many-to-many связь.
- Нормализованное название уникально внутри группы без учёта регистра и крайних пробелов, включая архив. При совпадении с архивной записью предлагай восстановление.
- Архивирование запрещает новые подключения, но не удаляет существующие связи и исторические данные.
- Удалять дисциплину можно только при отсутствии подключений и зависимых данных.
- Удаление дисциплины из периода удаляет только связь и также должно учитывать будущие зависимые данные.

### Занятия и посещаемость

- Занятие принадлежит конкретному периоду и дисциплине, уже подключённой к нему. `periodId` хранится явно.
- Типы занятия фиксированы: `lecture`, `practice`, `laboratory`, `seminar`.
- Дата занятия обязана находиться внутри периода.
- При создании фиксируется снимок всех активных участников группы, включая старосту и заместителей. Последующие изменения состава не меняют уже созданный снимок.
- Пара `lessonId + groupMemberId` уникальна.
- Статусы посещаемости: `present`, `late`, `absent`, `excused`; `null` означает «Не отмечено» и не
  является отдельным статусом.
- Массовые действия заполняют только `null` и никогда не перезаписывают ручные отметки.
- Полный сброс требует подтверждения и очищает статусы и комментарии, не удаляя занятие.
- Завершённость вычисляется: занятие завершено только при наличии статуса у каждой attendance-
  записи. Отдельный `isCompleted` не нужен.
- Незавершённое занятие в будущих расчётах должно исключаться целиком.

## UI и визуальные правила

### Общий стиль

- Интерфейс спокойный, учебный и утилитарный: светлые поверхности, умеренные границы, синий primary, семантические цвета только для статусов и предупреждений.
- Используй токены из `src/app/globals.css`, существующие UI-примитивы и Lucide-иконки. Не вводи локальные произвольные цвета, радиусы и тени без причины.
- Заголовки используют Manrope, основной текст — Inter.
- Не дублируй заголовок/счётчик секции отдельным блоком над вкладками или списком.
- Между label и контролом должен быть заметный воздух. Не прижимай поле к подписи; следуй существующим отступам формы.
- Ошибки конкретны и объясняют способ исправления. Мягкие предупреждения компактны и не требуют лишних кнопок. Success-состояния показывай ненавязчивым уведомлением.
- Меню и Dialog закрываются по клику вне области и по Escape. Меню не должно выходить за viewport.
- Вся область date-input должна открывать календарь, если браузер поддерживает `showPicker()`.

### Responsive

- Mobile-first. Проверяй минимум узкий mobile около 430 CSS px и обычный desktop.
- Touch target на mobile — примерно 44 px или больше. На desktop элементы могут быть плотнее, но не настолько, чтобы подписи выглядели зажатыми.
- Внутри группы desktop-навигация находится только в левом sidebar. Верхняя навигация разделов группы предназначена только для mobile. Вне группы sidebar отсутствует.
- Desktop-таблица допустима для многополевых сущностей; на mobile используй вертикальный список. Для сущности с одним основным полем предпочитай компактный список и на desktop.
- Не сокращай предметные подписи ради вёрстки. Используй адаптивные `min/max`, перенос или смену компоновки.
- Длинное имя участника может занимать максимум две строки, затем ellipsis; полное имя оставляй в доступном `title`/tooltip.

### Established interaction patterns

- На desktop действие создания периода — текстовая кнопка с конкретным типом периода; на mobile — компактный `+` с точным `aria-label`.
- Второстепенное редактирование периода находится в меню `…`, а не в отдельной основной кнопке.
- Для destructive-действия требуется подтверждение. Архивирование, деактивация и восстановление используют спокойные недеструктивные сценарии.
- Empty state должен соответствовать следующему доступному действию. Если CTA не нужен, показывай нейтральное сообщение без кнопки.

## Валидация, ошибки и время

- Используй Zod на границе ввода и повторно защищай бизнес-инварианты в сервисе.
- Нормализация выполняется централизованно до сравнения и сохранения.
- Ожидаемые конфликты преобразуй в типизированные service errors; неожиданные ошибки логируй без утечки секретов и показывай общее безопасное сообщение.
- Календарные даты храни и сравнивай как `YYYY-MM-DD`, не прогоняя через локальное время браузера.
- «Сегодня» определяется в IANA-часовом поясе пользователя. Не фиксируй UTC или часовой пояс разработчика как продуктовый источник истины.

## Проверки: только пропорционально риску

Не запускай автоматически полный набор тестов, production build и все доступные проверки после
каждой задачи. Выбирай минимальную проверку, которая надёжно подтверждает конкретное изменение.

- Текстовая правка или локальный CSS: обычно достаточно точечной проверки файла, `pnpm lint` или
  визуального осмотра затронутого viewport. Не запускай весь test suite и build.
- Локальная TypeScript/React-правка: `pnpm lint` и/или `pnpm typecheck`; запускай конкретный тестовый
  файл, если изменилось поведение.
- Изменение чистой domain-функции или схемы Zod: запускай соответствующий `vitest`-файл, а не все
  тесты.
- Изменение сервиса/репозитория: запускай тесты этого feature и typecheck. Полный suite нужен только
  при сквозном влиянии на несколько модулей.
- Изменение Drizzle-схемы: сгенерируй миграцию, проверь SQL и выполни релевантные schema/service-
  проверки. `db:check` запускай, когда задача действительно касается применённой схемы.
- `pnpm build` запускай только по прямому запросу, перед релизом/deploy либо когда изменение
  Next.js-конфигурации, маршрутизации или server/client boundary нельзя достаточно проверить
  более дешёвым способом.
- Полный `pnpm test` запускай перед значимым этапом/релизом или при широком рефакторинге, но не
  после каждой визуальной итерации.
- Не запускай повторно уже успешную проверку, если после неё не менялся относящийся к ней код.
- Не выполняй performance-аудит, browser-прогон всех сценариев, миграцию базы или внешние сетевые
  проверки «на всякий случай».

Если всё же требуется production build, сначала останови `next dev`, чтобы процессы не делили
`.next`, а после сборки снова запусти dev-сервер, если пользователь работает с localhost.
